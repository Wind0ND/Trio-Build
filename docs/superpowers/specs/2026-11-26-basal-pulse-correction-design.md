# 沿用原生SMB算法，以短时基础率执行：收敛设计

日期：2026-11-26，北京时间。状态：按用户最新意见收敛的设计；应用尚未实现本功能、未构建或发布。

## 用户已确定的方向

原有算法已经完善，本次沿用原生SMB算法决定是否给药、单次剂量以及相关基础率配套动作，仅改变SMB的执行方式：在支持的Medtrum基础率闭环场景，通过现有短时基础率模块模拟执行，再自动取消。用户明确要求取消失败采用最高级别有声警报，突破专注模式并启动系统闹钟。

本次不另做一套治疗算法，不添加剂量倍数、不改变个人治疗参数，不把长期观察模式或独立疗效研究项目扩成此次实施范围。必要的实现验证仍覆盖剂量一致性、防重复和取消失败路径。

## 本次只做四件事

### 1. 采用原生SMB决策

保留原有UAM预测、是否需要SMB、剂量、IOB额度、低值保护、SMB间隔及配套基础率决策。新增明确的替代输注能力入口，让算法输出SMB计划，由执行层选择短时基础率通道；不伪造泵具有bolus能力、不发送实际bolus命令。

保留当前药贴、输注状态、数据新鲜度及最终写前复核。普通SMB与基础率模拟不能同时执行同一次建议。

### 2. 复用短时基础率执行

抽取共用短时执行器，明确区分manual／automatic来源；不把自动给药冒充手动请求来绕过保护。复用现有截止计时、会话及段身份、持久化、到期取消和重连核对。

速率／时长换算只负责在设备和已保存上限内执行原算法计划，不创造额外剂量。不将手动30 U/h默认值搬成固定自动治疗参数，不自行提高上限。若某个SMB计划无法在这些限制内等效执行，本次不模拟，也不积压为后续补发；未下发泵命令时，可重新使用原有无SMB计算流程。

原SMB的基础率配套动作与短时输注必须由同一次执行协调，不能同时覆盖同一泵基础率或把原高基础率纠正量再叠加一份。

### 3. 保留实际记账与防重复

短时输注按真实开始、结束及泵段记录进入原有基础率历史和IOB，不同时记成一笔SMB和一笔临时基础率。确认结束后按当前状态重算下一轮，不重发旧剂量。

取消未确认或历史未明时，保留原有输注未知、待核对及防重复保护，并继续安全取消／同步；不能因为警报已查看就认为泵已停止，也不能无条件回退并继续追加。保留现有3分钟最短闭环间隔和已保存上限。

### 4. 取消失败升级为最高级系统闹钟

- 复用AlarmKit，明确critical严重程度和有声警报，不受App普通静音、提醒暂停或夜间静音影响；系统授权仍由用户决定。
- 新自动脉冲写泵前先确认闹钟授权并实际完成保护闹钟预排。失败时不启动这次新脉冲，原有基础率闭环继续按原流程工作；此检查本身不改泵内基础率日程。
- 系统看门闹钟提前排好；到期取消明确失败时立即报警，未确认结束时按预排截止报警。立即报警和预排保护去重，替换计划时不能留下无保护空档。
- 已经开始的输注，不得因为闹钟权限丢失或调度失败而停止取消处理；同时阻止下一次脉冲。
- 用户可以停止铃声，但不会因此清除输注未知和防重复保护。只有核实本次原输注段结束，才能解除对应事故并撤销对应闹钟。
- 现有手动短时请求在AlarmKit可用时也尝试预排；失败明确显示保障不足，保留既有手动能力及取消处理。新增自动路径仍要求预排成功。
- 闹钟负责提醒处理，不能自动让失联的泵停止；保留现有取消重试与保护，不把“有闹钟”记成已停止或安全性已验证。

原草案的结束后15秒确认宽限、停止铃声后60秒未解决再提醒仍为待实施核对的工程初稿值，用户尚未明确确认；不把这些值作为已批准治疗参数，也不由此延长目标输注时间。

## 必要验证与交付边界

实施只做与此次改动直接相关的验证：同一输入的原算法SMB计划一致；换算和实际历史不重复计量；既有手动短时不回归；预排成功才可启动新自动请求；启动／取消回复丢失、断连、重启和旧回调不重发／不误撤销；取消失败触发最高级有声警报，停止铃声不解锁。

编译、系统实际响铃和泵实际结束分别确认，不能互相代替；模拟SMB的输注时序与原生bolus不同，不把复用算法等同于已证明疗效和所有故障边界一致。当前未授权签名上传或发布新版本。
